### Local inventory and provenance proposal

Proposed `InstalledAppObservation` is local-only: random observation ID, canonical location plus original location/volume identity, user scope, bundle ID, validated code identity/Team ID, version and vendor version-comparator ID, architecture, channel/edition/paid generation, provenance status, observed time and individual evidence/error fields. Bundle ID alone is never a match. Numeric dotted comparison in the current fixture is insufficient for all vendor versions: unknown comparison semantics defer; each supported comparator is versioned and reviewed.

Keep inventory in an owned per-user Application Support namespace, directories 0700/files 0600, bounded to 10,000 observations. Proposed lifetime: current snapshot replaced atomically each completed scan, no historic inventory retained; inaccessible observations become unknown with last-seen time, then removed after 30 days or immediately when their explicit location is removed. Transaction journals/history are separate minimum recovery records with their own agreed retention. No shared root-owned inventory or cross-user catalogue matching. Licence machine allocation remains separate and minimal.

Enumerate application bundles within explicitly authorised roots, stopping at bundle boundaries, with bounded depth/count and no symlink or alias traversal outside roots. Distinguish duplicates by volume/file identity and path; same product in two locations stays two observations and needs explicit target selection. Ignore duplicate aliases to the same underlying file with an explanatory status. Permission denial, missing personal folder and offline/removable volume have distinct scan outcomes; no elevation or Full Disk Access request inferred. Removed volume/location invalidates queued candidates and requires re-observation after return. Destination ownership, containment and no-follow/TOCTOU checks occur again at install boundary; merely adding a location grants no write authority.

For App Store provenance, inspect available receipt and code-signature evidence locally with bounded safe reads. Receipt presence alone is not validation; receipt absence does not prove vendor-direct origin. Apple documents a receipt URL that can be missing/invalid, and recommends newer transaction APIs for an app validating its own download; those APIs are not assumed to validate arbitrary third-party apps. Build a reviewed conservative per-app detector, requiring validated receipt identity/signature where accessible plus compatible code identity, otherwise unknown. Do not refresh another app's receipt or request its account credentials. [Apple receipt API](https://developer.apple.com/documentation/foundation/bundle/appstorereceipturl).

Use only operator-approved, fixed `https://apps.apple.com/.../id<reviewed-id>` links, opened on explicit customer choice. Prefer a verified Mac product URL; if ID or native handoff is unsupported, offer the App Store itself with search instructions. No user-supplied scheme/redirect or link claiming the installed app is current. Apple's [archived link guidance](https://developer.apple.com/library/archive/qa/qa1633/_index.html) supports store-link construction, not proof of current macOS deep-link behaviour; real supported-OS handoff is a required native test.

### Catalogue distribution and optional support proposal

Proposed public paths are relative to an owner-approved future catalogue origin: `GET /v2/catalogue/current` and `GET /v2/catalogue/revisions/{sequence}/{digest}.json`. Neither accepts app IDs or inventory. ETag/conditional checks use global catalogue revision only, with no customer-specific cache key. Proposed client check cadence is at explicit Check and at most every six hours while eligible background checking exists; no timer is added here. Target a compressed response below 256 KiB and hard reject decoded envelope above 2 MiB/payload above 1 MiB. If coverage outgrows this bound, redesign global distribution and limited-data budgets before implementation; do not silently introduce per-installed-app queries. No automatic full download on a constrained network when it exceeds the accepted small-check budget; retain accurate last-checked/stale state.

Cache exact authenticated bytes and durable high-water mark per catalogue, separately from disposable inventory. Same sequence is valid only with identical payload digest; lower sequence, missing/corrupt state, unknown/retired key, wrong domain/catalogue, unsupported schema, incompatible app version or invalid clock refuse new candidates. Fresh app setup is an explicit authenticated bootstrap; normal state loss never resets replay state automatically. Same-user rollback of a complete local state backup and hostile system clock are residuals, as in fixture proof; production must test trusted-time/checkpoint strategy rather than imply local files resist their owner. Expired cache may explain historical observations with a stale label, never authorise a new install. Service unavailability preserves safe recovery and independent self-update access.

Proposed separate request endpoint `POST /v2/support-requests`: schema version, app display name (128 characters), bundle ID if observed (255), claimed vendor/product URL only if supplied and approved as inert text (2 KiB), optional observed version only when preview includes it, client request UUID and consent schema/version/time. Optional plain-text notes (proposed 1000 characters and at most 2 KiB) and vendor website URL are accepted fields, previewed with detected app details; no file attachments. No path, username, full inventory, licence/device ID or automatically collected logs. Household ownership is derived from the verified session by an authenticated service boundary, never a caller-supplied account ID or checkout contact email. Server distinguishes `locallyObserved`, `userSupplied` and later `independentlyVerified` evidence. Redact sensitive URL tokens/personal paths where feasible and preview the exact resulting sent payload. Context never grants source approval or privileged fetching. Further fields/file uploads need separate scope; notes/URL no longer wait on owner policy, but exact validation/retention/privacy contract remains proposed.

Preview exact outgoing fields, purpose (coverage research), destination (Patched catalogue support service, operator access only), retention and cancellation before submission. Proposed retention: raw requests 90 days, coalesced non-personal research identity/status 12 months; security request logs seven days with bounded pseudonymous abuse counters, no raw IP/body/path stored in application logs. Provider network logs may exist and must be disclosed/configured; local matching does not make vendor/network metadata invisible. Request retention is proposed, not settled privacy policy.

Reject unknown fields, oversized/malformed bodies (8 KiB cap), injection and forbidden schemes; render plain text escaped, never auto-fetch a supplied URL or execute code. Proposed abuse limit: five submissions/hour per short-lived network abuse bucket and per verified household, duplicate UUID idempotency 24h, product duplicate coalescing without exposing another customer's fields. No fingerprint used for licensing. Precise edge controls and legitimate shared-network behaviour need tests. Return opaque request ID plus `received`; `GET /v2/support-requests/status/{requestID}` and authenticated list/detail routes derive the household from verified sign-in and check ownership on every read/write. A request ID is not bearer authority. Foreign and unknown IDs return the same refusal; exclude identifiers/tokens/bodies from logs and private responses from caches. No paid entitlement is required and sign-in never starts trial. Session validation should use a narrow licensing authorization interface, not a catalogue-support binding with broad licence DB access; its exact audience, expiry/revocation and unavailable-service behavior require contract acceptance before integration. Persist private status across client restarts/account sign-in; duplicate/global research coalescing exposes none of another requester's notes/account. Proposed states Received, Under review, Verification pending, Published support, Held, Unsupported and Rejected follow actual evidence; Published requires verified committed/readback support, not research completion. Deduplicate meaningful in-app completion by requester/request/verified support revision and handle incompatible/withdrawn/expired support honestly; notification denial retains in-app status. Client newly supported-apps page and PAT-2611 website projection share authoritative public-safe published support metadata, separate from private request details and ordinary version updates. Requester-only opted-in email remains later PAT-2610; no broadcast or launch email/SMS authority.

## Signed contract, freshness and atomic publication proposal

Production v2 envelope remains strict exact-key JSON with canonical base64 payload/signature. Domain separation `im.patched.catalogue.v2\0` plus exact payload bytes. Signature algorithm proposed Ed25519, not a reused fixture trust object. Payload contains schema/domain/catalogue/key IDs, global sequence, issued/expiry, minimum compatible Patched protocol/build, policy digest, sorted complete entries and withdrawal records. Each entry binds product/bundle/developer/source identity, version/comparator, stable channel/edition/generation, OS/architecture, approved vendor URL/redirect hosts, artifact hash/length, evidence digest/policy/checker versions, independently observed verification time/valid-until, installer method and tested interaction/restart/coordination rules. Eligibility is an explicit local result, not a signed `installAllowed` boolean. Untrusted local purchase assertions never grant free-paid-update eligibility.

Proposed security parameters: catalogue 48h lifetime (below current fixture's 72h maximum but a new contract); time skew at most five minutes; live native freshness-dependent assessment maximum 72h, shortened by vendor/policy expiry; latest source observation at most 24h at signing; `expiresAt <= min(issuedAt+48h, all included evidence.validUntil)`. Exclude expired entries or publish a withdrawal revision rather than extend them. These are reviewable starting parameters, justified to tolerate short VM downtime while placing a finite stale-install window; measurements may shorten them, never silently lengthen them. Cryptographic byte/signature evidence may be cached for unchanged bytes under explicit versioned policy, but current revocation/Gatekeeper/source status and compatibility checks must be renewed by actual assessment. Re-signing cannot change original observed times or create freshness. If no valid entries remain, serve signed empty/withdrawal catalogue while possible; otherwise fail closed with accurate degraded status.

Publisher submits only `{intentID, evidenceIDs, acceptedPolicyDigest}` to `reserveAndSign`; no arbitrary payload or times. Signer owns assembly and allocation in its D1 primary. Reserve immutable `{catalogueID, sequence, intentID, payloadDigest, policyDigest, evidenceDigests, issuedAt, expiresAt}` using unique catalogue/sequence and intent constraints plus atomic conditional update/batch. Sequence is never decremented/reused after reservation, including crash gaps. Same intent can return exact stored bytes only; any conflicting fields refuse. Critical signer reads go to primary, not stale replicas. Policy/evidence/key state rechecked before signing; storage failure before durable immutable reservation prevents signing. Store exact signed envelope before returning. Publication intent is invalidated when policy/evidence/withdrawal state changes; do not trust a stale signed reservation after its underlying approval is withdrawn.

No cross-resource transaction between D1 and R2 is assumed. Stage content-addressed catalogue and private evidence objects; recompute exact-byte digest and verify envelope on fresh R2 read. Create public immutable revision under `v2/revisions/{sequence}/{envelopeDigest}.json` with conditional create, verify again. Commit current revision in D1 only with compare-and-set against expected previous revision, accepted intent and unchanged policy; competing publisher retries against fresh head, never overwrites/decrements it. Public `current` API resolves committed head through primary state and returns its exact signed envelope. Missing/mismatched object yields 503/degraded, never unsigned fallback or partially staged bytes. CDN caching may serve an older signed revision; keep current response `no-store` initially, immutable revision caching bounded by signed expiry, and test both normal and cache-bypassing readback.

A separate readback verifier without signer/write access fetches the actual public origin/current/revision, verifies signature against app-distributed public keys, expiry/sequence/digest and records response identity/time. Hosted success is only `readback-confirmed`, not signer return, R2 PUT or commit. Readback failure alerts and blocks success; if bad head must be removed, publish a higher-sequence withdrawal/fixed revision, never point to old catalogue. Clients may already have received committed content before readback; the signer/consumer checks must be safe independently. R2 is strongly consistent for object operations but cached public content can lag; this protocol does not infer multi-object atomicity. [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).

Withdrawal adds a new signed higher sequence naming affected artifact/release identities, reason and effective time; remove eligibility locally and discard not-started work after refresh. No downgrade or rollback to a previously signed catalogue. Native safe rollback of a transaction is a separate recovery action, not permission to offer an older release. Offline clients cannot instantly learn withdrawals; expiry bounds honest stale-cache use, not malicious signing-key compromise.

## App-distributed trust and recovery proposal

Proposed `Resources/CatalogueTrust/catalogue-trust.json` ships inside signed Patched releases; table fields: trust-set version, catalogue ID, key ID, exact 32-byte public-key digest/value, signature algorithm/domain, introduced app build, first/last allowed sequence and retired status. Real values are deliberately absent here. Bundle sealing plus independently authenticated Developer ID/notarised initial distribution establishes bootstrap; HTTPS download alone or the catalogue service's own key endpoint does not. Confirm legal Team ID/certificate access under PAT-7 and release manifest/feed/artifact path under PAT-2609. Apple's [notarisation guidance](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) requires Developer ID signing and distinguishes notarisation from App Review; it is separate from catalogue signatures.

Ordinary rotation: release app B containing old K1 and new K2 plus explicit permitted sequence ranges; independently deliver B through Sparkle/application release trust. During measured transition serve compatible K1-signed revisions only while K1 remains approved and evidence fresh. At recorded cutover sequence N start K2; old A knowing only K1 fails unknown-key with “Update Patched to check for app updates”. Later app C removes/retires K1 entirely; C rejects K1 even for validly signed higher sequences. All builds must keep global high-water continuity across keys. No indefinite dual-key fallback or automatic K1 reintroduction. Exact app build/sequence mapping and cutover dates are release facts requiring acceptance and compatibility tests, not guessed here. V2 full catalogue can include minimum compatible app build; old clients cannot be trusted to obey fields they cannot authenticate.

Compromise differs from routine rotation: stop signing/publication, disable compromised invocation/deployment access under incident authority, preserve audit/evidence, verify independent app release channel and ship recovery app removing K1. Do not use K1 to authorise K2. Existing A offline/unupdated can accept attacker-generated K1 catalogues with fresh expiry; 48h catalogue expiry does **not** contain this. A malicious maximum sequence may poison old high-water state. Recovery app must carry separately authenticated new trust epoch and explicit recovery checkpoint migration, with reviewed scope and no automatic reset on ordinary missing state. Refuse old epoch after migration. Independent secure download/recovery instructions must remain reachable even if catalogue origin/key is compromised. Sparkle/feed, Developer ID and catalogue authorities must not share compromised credentials. If app-release trust also fails, follow separate PAT-2609 manual independently authenticated recovery, not catalogue fallback. Customer opt-out/offline status leaves a residual old-client window until independently updating or manually recovering.

Dedicated signer software custody means the runtime/deployer may misuse the secret; it is not HSM isolation/non-exportability. Proposed backup procedure before activation: Andy chooses encrypted offline owner vault plus separately held recovery passphrase and second encrypted copy outside the account, records access location/custodian/recovery steps without values, then restores into isolated non-public recovery signer with production invocation disabled. Verify restored public-key fingerprint and signatures against harmless fixed recovery challenge, reject wrong passphrase/corruption/wrong key, destroy temporary access under explicit authority and document only non-secret evidence. Restore must preserve highest signed/published sequences from independently retained audit; unknown/rolled-back checkpoints stop signing until reconstruction, never reset to zero. Rehearse loss of CF account and primary backup before production, and repeat after rotation. No keys are read, generated or backed up in this design task. Backup does not solve a compromised signing key; rotate via independent app trust.
