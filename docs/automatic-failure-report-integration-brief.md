## Proposed payload and producer boundary

Introduce a distinct closed `automatic-failure-report-v1` wire with purpose `failed-update-diagnostics`, not the coverage or manual-support schema. Maximum encoded UTF8 body 8 KiB; reject unknown fields at every level, duplicate keys, malformed Unicode/UTF8, controls, BOM, trailing data, depth over eight and noncanonical integers. Use unchanged strict JSON mechanics where appropriate. UUID representation must be fixed by independent vectors; explicit conversion from Activity's uppercase canonical IDs must not silently change identity.

Proposed root fields are exactly `{schema,purpose,reportID,eventID,attemptID,observedAt,policyVersion,app,client,error,diagnostics}`. IDs are random correlations scoped to one local user and failed attempt, never stable machine/account identifiers or bearer authority. `observedAt` is a nonnegative safe integer observation, not trusted server time. `policyVersion` is an accepted finite disclosure/schema version.

`app` contains exactly `{catalogueProductID,fromVersion,toVersion}` from an accepted failed-update producer and validated catalogue identity. Each value is nonempty, at most 128 Unicode scalars/512 UTF8 bytes, further restricted by an independently frozen vocabulary/grammar. Refuse unexpected personal-path, email, URL or secret-shaped identity/version values rather than forwarding arbitrary installed metadata. A verified display-name projection may be added only through an accepted schema revision; do not upload Activity appName/targetKey wholesale.

`client` is exactly `{patchedBuild,osMajor}` with a bounded approved build identifier and supported integer OS major. `error` is exactly `{component,code,phase}`, all independently enumerated safe values, with an explicit finite unknown value. `diagnostics` is at most 16 structured records and 4096 encoded bytes, each exactly `{component,code,phase,sequence}` using finite vocabularies and a bounded integer sequence. No freeform message, raw log, stack, journal, child stdout/stderr, path, inventory, token, email, hostname, proxy username/password, credential reference, header or URL field is permitted.

Generate diagnostic text for View report from these safe structured records. Omission/allowlisting precedes encoding; pattern redaction is additional refusal defence, not proof arbitrary text is anonymised. Revalidate the same whitelist and bounds server-side. Instrument body, header, URL, error, log and crash sinks; report identifiers may still be sensitive correlation data and stay private.

Only accepted failed-update outcomes qualify. Skipped, deferred, unknown/readback-unavailable and safely recovering outcomes are not automatically rewritten as failed. A future producer must distinguish outcome, provenance and recovery safety; sending a report neither authorises an update nor interrupts completion/recovery. Existing synthetic events can exercise fixtures only, with explicit synthetic provenance outside any production admission. No fixture marker or caller boolean issues native authority.

## Proposed consent, durable queue and retry

Setup and Settings → Diagnostics show “Automatically send failed-update reports”, initially ON for genuinely new accepted settings, with categories, destination and retention disclosure available. Persist the per-user switch, disclosure version and monotonically increasing generation independently of account/session, coverage, manual diagnostic choice, analytics, helper permission and update exclusions. Corrupt/missing previously established state or uncertain readback blocks sends; it must not silently reset a prior OFF choice to ON. Re-enable covers future failures only.

Enqueue only under current enabled generation after safe payload projection. Persist report ID, event/attempt correlation, frozen exact bytes and digest, generation, destination-policy version, creation/expiry times, retry count and state in one private per-user queue transaction. One report per accepted failed attempt; repeated producer callbacks reconcile the existing identity instead of minting new reports. Atomic commit plus exact readback precedes “Waiting”; failure leaves reporting unavailable without blocking update recovery. Proposed bounds: 100 reports/1 MiB, seven-day unsent expiry and seven actual dispatch attempts. Capacity refusal is visible and never silently evicts an uncertain send. Unsafe/unknown time prevents new dispatch until age can be established; relaunch cannot reset age or retry count.

One fenced worker leases a report. Revalidate enabled generation, frozen digest, expiry, destination and current PAT-2666 network admission immediately at the actual dispatch sink, not just when scheduling. A proposed backoff sequence after failed attempts is 30 seconds, two minutes, ten minutes, one hour, six hours and 24 hours, respecting longer server backoff without extending expiry. Offline/proxy denial waits without creating a transport; rapid reconnect does not bypass backoff. Exhaustion/expiry is terminal until a separately explicit new workflow, not automatic resend under a new ID.

Opt-out immediately latches an in-memory deny fence, advances durable generation and cancels/deletes all not-handed-off queued/retry work. Dispatch and withdrawal must share one serialised final-admission boundary; cancellation after an earlier check is insufficient. Failed persistence/readback keeps denial latched and displays incomplete cleanup; restart with uncertain state refuses. Old workers and callbacks cannot restore consent, requeue, or publish a stale success as a current send. Already handed-off bytes may have reached the service: record that uncertainty and reconcile without uploading the body again. Never promise recall of already delivered data. Remote deletion is a separate explicit capability, with its own pending/confirmed state.

All attempts use PAT-2666's single shared policy: system proxy by default, explicit direct/manual modes, secure credential references, current revision, fixed accepted destination, TLS and bounded response/time/redirects. No direct fallback after proxy/PAC/authentication refusal and no root/helper report networking. Network reconfiguration preserves identity/bytes but invalidates stale admissions. Authentication and reachability are not consent; raw proxy errors never enter diagnostics.

## Proposed shared intake, acknowledgement and access

PAT-2034 should own one shared intake, durable receipt/deduplication mechanism and eventual provider outbox for manual requests and automatic failure reports. PAT-2665 owns this distinct report schema, consent and client queue; PAT-2664 owns manual form/reply-contact semantics. Reconcile the manual draft's `services/manual-support/` directory naming before code; proposed common mechanics live under `services/support-intake/`, with separate closed purpose parsers. Share ownership and mechanics without widening coverage wire or making automatic reports depend on manual reply email.

Exact backend destination, account-free authorisation/abuse controls, access roles, storage, retention/deletion and any Linear projection remain proposals. Defaults refuse. Propose opaque per-report receipt/deletion capabilities, separate from reportID, no account/email requirement and no cross-report enumeration. Secure native capability storage and server hashing/constant-time verification need independent acceptance. Report UUID, app identity, Activity context and fixture provenance authenticate nothing. Do not reuse licensing sessions, catalogue trust or fixture principals as real report authority.

The service independently validates bytes/purpose and atomically stores the request, digest, private receipt ownership and pending downstream outbox. Return durable acknowledgement only after committed readback. Deduplication binds accepted client scope/capability, purpose and reportID to server-computed exact-byte digest: identical retry returns the original receipt; changed bytes conflict, never overwrite. Parallel duplicates have one effect. Lost/unknown acknowledgement retains identity and enters uncertainty; capability-bound receipt lookup or same-byte idempotent admission reconciles it. No new report ID for transport uncertainty.

Durable intake receipt is distinct from later Linear/provider delivery. Service success/local-mark crash or ambiguous provider response enters delivery uncertainty. Use the manual draft's persisted opaque marker, exact projection digest and complete authorised reconciliation; no blind provider-create retry. An empty/incomplete lookup is not proof of no creation. Client retries stop after validated durable intake receipt; the service alone owns downstream retries.

Propose requester capability access to this report's receipt/deletion, restricted support-operator access to redacted diagnostics and triage-agent access only to an accepted minimal provider projection. Unknown/foreign capabilities receive equivalent refusals. Service logs contain finite reasons/counters, never bodies or capabilities. Destination policy acceptance must define hosting, operators, access audit, rate/byte caps and abuse handling without requiring an account/email.

Propose local unsent expiry seven days, local acknowledged payload expiry 30 days, and service redacted diagnostic retention 30 days from receipt. These are unactivated values; Activity's independent history retention remains unchanged. Dedupe tombstones must outlive every accepted client retry/restore horizon and retain only approved minimal evidence. Owner policy must settle exact tombstone lifetime, backup retention, provider copies, unresolved-delivery maximum hold and deletion scope before real delivery. Expiry/deletion fences workers, invalidates capabilities, removes payload/projections and prevents delayed retry or restored backup resurrection; necessary retained evidence must be disclosed. A deletion acknowledgement never means deletion completed.

## Proposed truthful Activity and Help presentation

Project report state from durable report evidence separately from update outcome. “Waiting” means committed local work, with offline/proxy/backoff reason; “Sending” means current admitted attempt; “Sent to Patched” requires verified durable intake receipt. Display downstream delivery separately as pending/uncertain/delivered only with service evidence; never label intake acknowledgement “Delivered to Linear”. “Failed” exposes bounded refusal/exhaustion; also distinguish reporting OFF, expired, cancelled, unavailable and delivery unknown. Switching OFF must not hide an earlier confirmed receipt or rewrite history as never sent.

View report shows the exact frozen redacted payload, report reference, destination/disclosure version, retention/expiry and current evidence-backed status. It sends nothing. After payload deletion/expiry, show that content is unavailable without reconstructing it from raw logs. Settings changes and tab opening send nothing.

Get help only prepares the sole manual form, preserving its local email/message and diagnostic choice with a safe report correlation/state. It does not resend the automatic report, auto-submit or inherit automatic ON as manual consent. Manual Submit and its diagnostics boundary remain separate. Keep existing synthetic Activity checks unchanged; add a new report projection/controller instead of reinterpreting their injected `sent` label.
