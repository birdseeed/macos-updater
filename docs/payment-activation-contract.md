# Payment activation and household ownership contract

PAT-2587/2588/2589/2590/2605, final owner decisions 9 October 2026. **Accepted experience, proposed technical design, no implementation authority.** Reconciliation base `f4cf3f3638880bfd0fb98347e89c5f39c1517116`. Companion licensing, allocation, billing and support contracts retain their safety, expiry/revocation, five-active-Mac, shared-Mac, recovery and privacy rules. This contract supersedes blanket verified-email-before-paid-activation wording; it does not change the explicit verified-email no-card trial or valid private beta.

## Separate authority classes

| Flow | Required evidence and authority |
| --- | --- |
| Account-free discovery | No consumer session, payment, activation key or email ownership; local inventory and public signed catalogue matching. |
| Explicit Start trial | Verified household email session, unused authoritative trial history and explicit action; active beta preserves unused trial. Sign-in/payment/code entry alone never starts it. |
| App-originated paid purchase | Server-created checkout bound to protected installation possession; authoritative confirmed payment; uniquely consumed claim and guarded slot allocation. No pre-purchase email verification or licence-key copying. Grants only the purchasing installation's paid access until household ownership is verified. |
| Website-originated purchase | No presumed installation binding. One-time code to purchase email establishes possession, combined with authoritative payment, fresh installation possession and guarded household/slot binding. No licence-key copying. |
| Household control | Verified ownership for another Mac, recovery, sensitive actions and private app-support requests; support requests need no active paid entitlement. Payment email alone is receipt/contact information, never account authority. |

Initial paid access is not automatic third-party install consent. Each new transaction still checks valid lease/activation, trusted catalogue/artifact, exact compatible route, permissions, opt-in/exclusions/skip/pause as applicable and safety. Finishing/recovery never requires renewed payment. Patched self-update remains separate.

## Proposed app purchase protocol

1. Explicit Buy creates a protected installation key lazily through PAT-2605 machine-key/helper boundary (or its accepted fallback); never require it for scanning. `POST /v1/purchase-intents` accepts a purpose-bound signed server challenge, installation public-key digest and idempotency UUID. Validate possession and approved offer/environment server-side. Client-supplied email, account ID, price or provider ID is not authority.
2. Service creates a random >=256-bit claim secret, stores only its digest, binds intent to installation key, environment, server-selected offer, expiry and optional *already verified* session owner. Proposed checkout-creation claim lifetime30minutes; payment processing may outlast it, but must use a fresh possession challenge before fulfilment. Return an approved HTTPS checkout URL and restricted status capability over authenticated TLS; keep secrets out of URL queries, analytics, logs and clipboard. Browser redirects carry no granting proof. Exact Paddle checkout/custom-data mapping and persistence must be verified before enabling.
3. Verified Paddle webhook intake and authenticated API reconciliation resolve the server-recorded transaction/offer/environment and current paid/refund/revocation state. Unknown, pending, cancelled, mismatched or ambiguous states grant nothing. Client-reported success/transaction reference never creates a mapping. Persist verified event IDs and reconcile current state rather than trust delivery order.
4. `POST /v1/purchase-intents/{intentID}/claim` proves fresh possession bound to intent/nonce and claim digest. A single guarded transaction conditions intent/payment version, unconsumed claim, installation identity, ownership revision and slot capacity. It consumes once, creates/reuses one activation and records the paid source/lease issuance outcome. Unique `(env, providerTransactionID)` and `(intentID, installationKeyDigest)` prevent duplicate purchase owners and slots. Lost replies return current stored outcome after possession revalidation; they do not replay a granting lease after refund/revocation.
5. Without verified ownership, create one opaque **pending purchase owner**, uniquely linked to that transaction, with the shared account/activation guard and capacity semantics. Map its stable opaque `purchasePrincipalID` to a stable provisional `accountID` and existing `account_guard`; leases remain signed standard envelopes binding that accountID/activation/key, never an unsigned or ad-hoc grant. Ownership verification preserves that identity on promotion, or uses a reviewed guarded transfer/new lease revision. Its installation-scoped session may refresh only its own lease, view its own processing state and request ownership verification. It cannot enumerate/change household Macs, access private support, recover accounts, change email/billing or export claims. Receipt email is stored separately with `ownershipVerified=false`. Proposed restricted session15minutes with possession-based renewal and revocation; not a household sign-in session.
6. An already verified session may attach purchase to its existing household only when the server bound that session at intent creation, it remains valid and slot checks pass. Checkout email changes never change that owner. Otherwise email matching neither discovers nor merges an existing household. Show generic verification-required state, no existing-account details. After email verification, an explicit guarded ownership resolution either promotes the pending owner or requests an authorised transfer to an existing household; capacity, shared-machine reuse, paid-source uniqueness and both guards must be checked together. Proposed service-wide claim/transfer coordinator uses the existing guard transaction, not independent read/write calls. No silent merge or overwrite; over-cap/conflicting ownership holds transfer for explicit safe resolution while preserving lawful existing paid access.
7. Installation loss before consumption needs fresh verified email ownership plus the same authoritative payment and normal recovery controls, not a transaction screenshot or support-disclosed code. Loss after consumption uses ordinary recovery; replay onto a different key fails. Payment finishing after expiry is retained as paid-but-unclaimed, then recovered by verified ownership. Retry/cancel/restart never creates another subscription, starts trial or releases a slot silently.

Proposed closed challenge fields: `schema=1`, `purpose` (`purchaseIntent`, `purchaseClaim`, `purchaseOwnership`, `websitePurchaseActivation`), `env`, `intentID` where applicable, installation key digest, nonce digest, issued/expiry and consumed revision. Proposed restricted session fields: opaque digest, provisional accountID, activationID, installation key digest, `sessionKind=purchaseInstallation`, fixed allowed operations, issued/expiry and revocation revision. These are new schema/purpose proposals requiring parser/SQL review; existing auth/activation challenges cannot be reused across purposes. Pending ownership is a bounded purchase ledger state, not a second household created by matching email. Promotion/transfer must preserve one purchase source, slot history and trial/beta history. Exact compatibility with current proposed `accountID`/lease schema must be frozen and proved jointly by licensing/allocation fixtures before P1 enables any claim. Do not declare this schema accepted or existing.

## Website purchase activation

`POST /v1/purchase-activation/challenges` accepts bounded email input and a fresh installation-possession challenge; generic response regardless of purchase/account existence. Server associates a pending challenge with an eligible reconciled website purchase without revealing it. Proposed code10minutes, five attempts, issuance/rate budgets from sign-in contract, hashed code storage and single-use conditional consumption. No support/operator-readable code, ordinary logs or analytics. Delivery is a future explicitly scoped service action, not performed by this plan.

`POST /v1/purchase-activation/verify` verifies code possession and installation challenge, then requires authoritative confirmed entitlement and capacity through the same guarded claim protocol. A code alone cannot grant payment, trial, slot or arbitrary household access. Email already owned by a household requires verified account-bound resolution; wrong email receives generic failure. Concurrent attempts on two Macs cannot both consume the same initial claim; adding another Mac thereafter needs verified household control and normal allocation. Codes belong only in the authenticated product flow, never support chat. Payment delay, expired/replayed code and lost responses yield safe processing/retry, not guessed access.

## Shared atomicity, privacy and provider proof

All activation, pending-owner promotion/transfer, billing/refund/revocation, support recovery and slot writers use the existing proposed shared `account_guard`/activation revisions and nonce-fenced conditioned D1 batch rules. Transfers touching two owners require a jointly validated transaction; if the provider/store cannot guarantee it, hold transfer rather than split commits. The same shared physical Mac reuses one household slot after protected identity proof; per-user sessions remain isolated. Five active slots and duplicate-request conflict semantics apply to both flows.

Provider events authenticate origin via [Paddle signature verification](https://developer.paddle.com/webhooks/about/signature-verification/); current state can be reconciled with [Get a transaction](https://developer.paddle.com/api-reference/transactions/get-transaction/). These documented APIs do not prove Patched's selected checkout, custom-data association, sandbox configuration, scopes, notification delivery or current live approval. Verify those exact capabilities in approved sandbox before enabling. Never treat redirect/custom-data email or a client-side token as payment or ownership authority.

Proposed claim rows retain digests/opaque IDs and minimal payment mapping under existing financial retention review; expire unused challenge secrets promptly, never log bearer material. Pending paid ownership retention/deletion and customer copy require privacy/financial review. Email verification/send/provider credentials, purchases and actual installation retain separate gates. No Widgetter mechanism is claimed.
