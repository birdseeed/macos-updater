# Native menu integration

`PatchedApp` composes a native `MenuBarExtra` and the `patched-main` WindowGroup over one retained `NativeClientSession`. App-owned mutable insertion state starts true and uses the multi-scene binding overload. The menu label eagerly renders the existing `ShellBrandMark` at 2x into a bitmap-backed, 18-point template image for native tinting. Image-generation refusal adds no substitute asset. The menu uses system fonts and literal text.

The five explicit menu actions are Scan, Updates, Applications, Activity and Settings. Scan calls the session's existing applications controller, preserving its singleflight guard and current destination. The route actions select the existing navigation destination and request the main window, including when that destination is already selected. Repeated selection retains the navigation object's existing no-op behaviour. Window opening and application activation belong to the view's user-action callback, outside the session API. Both scenes retain the same applications and inspection owners, settings drafts and selected settings section.

An inert marker attached to the main root view records a weak reference to its own containing window in an App-owned adapter. A route gesture brings that window forward when it still exists; otherwise it requests the named WindowGroup. A pending-open flag coalesces requests in the current main-queue turn. Attachment clears it immediately, and a next-turn callback resets only that flag so a later explicit gesture can retry if no window attaches. Neither callback opens or activates a window or starts work. The adapter neither enumerates application windows nor searches identifiers, and it adds no window authority to the client session. Native acceptance must confirm repeated gestures, closing and reopening, and attachment timing.

The menu observes the applications controller directly so its mounted view can redraw on inventory publication. Status, observation time, provenance, Scan title and enabled state come from that controller's actual display projection. Refreshing retains the controller's previous-observation explanation. Inventory observations, including an empty scanned folder, do not establish update readiness: the separate `MenuSummary` remains unavailable with no counts or checking-for-updates claim.

The application delegate adopts an explicit policy that closing the last window keeps the current user session alive for menu access. Explicit Quit retains the ordinary application behaviour. This policy adds no persistence or restart promise. Background checks and notifications remain unavailable; closed-window menu access does not promise background updates. Construction and rendering start no scan or other work.

The delegate also sends Dock/Finder reopen events to `NativeClientReopenCoordinator`. Registration replaces the retained opener without invoking it. With visible windows, or before registration, the handler permits normal framework handling. Otherwise it invokes the opener once and suppresses duplicate framework creation. The main root's native marker registers the same window adapter and retains only that adapter plus the SwiftUI scene-opening action, so closing the root does not discard the route or retain the registering view. Registration and attachment never activate the app; activation belongs to an explicit menu or reopen gesture. This source correction and its callback/bitmap checks do not establish a visible status item or successful real Dock reopening; exact-binary native acceptance remains required.

This source slice adds no update execution, scheduling, service, login item, notification permission or delivery, account, network or installation operation. It does not complete the notification journey. Source bindings and offscreen rendering cannot establish native menu, focus, accessibility, close/reopen or lifecycle behaviour. Those need separately recorded operating acceptance against the exact source and binary. No build, test or native operating result is claimed by this document.
